# Locora app

Tauri 2 backend (`src-tauri/`) and Leptos UI (`ui/`, WebAssembly via `trunk`), with
shared IPC types in `shared/`. Its own Cargo workspace, so the main workspace builds
without WebKit/GTK.

## Once: tools and system packages

```sh
rustup target add wasm32-unknown-unknown wasm32-wasip2
cargo install trunk --locked
cargo install tauri-cli --version "^2" --locked
# Linux, Fedora (Tauri 2 prerequisites):
sudo dnf group install "c-development"
sudo dnf install webkit2gtk4.1-devel gtk3-devel libsoup3-devel javascriptcoregtk4.1-devel \
  openssl-devel curl wget file libappindicator-gtk3-devel librsvg2-devel libxdo-devel pkgconf-pkg-config
# Linux, Debian/Ubuntu (Tauri 2 prerequisites):
sudo apt update
sudo apt install build-essential curl wget file pkg-config libwebkit2gtk-4.1-dev libgtk-3-dev \
  libsoup-3.0-dev libjavascriptcoregtk-4.1-dev libssl-dev libxdo-dev libayatana-appindicator3-dev librsvg2-dev
```

## Start and build

```sh
cd apps/app
cargo tauri dev      # starts the UI dev server and the app window, rebuilds on change
cargo tauri build    # release build + installers in target/release/bundle/
```

On the desktop the app opens the same profile as the CLI (`$LOCORA_DATA` or the platform
data folder). To try it without touching your own palaces:

```sh
LOCORA_DATA=/tmp/locora-test locora tutorial
LOCORA_DATA=/tmp/locora-test cargo tauri dev
```

## Mobile builds (Tauri 2)

[Mobile builds](../../.github/workflows/mobile.yml) runs Android on pushes to `main` and `testing`,
pull requests and manual dispatch; iOS (macOS runner) only on manual dispatch to save
Actions minutes. Both jobs build the Trunk frontend and the official
Core/Review WASI plugins, then compile the native app. No Node toolchain is needed.
The workflow pins Tauri CLI **2.12.3** and Trunk **0.21.14**; update the mobile SDK
versions together with the CLI's generated templates when upgrading.

Native projects are generated by `init` on each clean runner under
`src-tauri/gen/android` and `src-tauri/gen/apple`; they are not checked in. For local
work, run `init` once and keep those directories if you customize native settings.
Do not regenerate over native customizations without reviewing the changes.
The backend already has the mobile entry point and static/dynamic library targets.

### Mobile app icons

The replaceable icon source is [`assets/brand/icon.png`](../../assets/brand/icon.png).
[`assets/brand/mobile-icon.json`](../../assets/brand/mobile-icon.json) sets the
iOS background color and the Android adaptive-icon background. After replacing
the square source image, regenerate the tracked Android and iOS icons with
Tauri CLI and ImageMagick (`magick`):

```sh
./apps/app/scripts/generate-mobile-icons.sh
```

The generated files live in `src-tauri/icons/android` and `src-tauri/icons/ios`.
The Android build script also copies the tracked icons into an existing local
Android project. A clean iOS `init` picks up the tracked icons; if an iOS project
already exists, regenerate or update its `AppIcon.appiconset` after changing them.

### Android: ARM64 debug APK

Requires JDK **21**, Android SDK command-line tools and accepted SDK licenses.
Set `JAVA_HOME` and `ANDROID_HOME`; Tauri uses **`NDK_HOME`**, not just
`ANDROID_NDK_HOME`. With this pinned CLI the templates use Android API **37**,
build tools **37.0.0**, NDK **29.0.13846066** and Gradle **9.6.1**.
CI's Android setup action accepts the licenses. Locally, the build script asks for
license acceptance, installs the pinned SDK packages and Rust targets, generates
the Android project on first use, and builds an ARM64 debug APK:

```sh
./apps/app/scripts/build-android.sh  # from the repository root; no phone needed
```

Install JDK 21, [Android SDK command-line tools](https://developer.android.com/studio#command-line-tools-only),
Tauri CLI 2.12.3 and Trunk 0.21.14 first. Put `sdkmanager` on `PATH`, set
`ANDROID_HOME` to the SDK directory, and set `JAVA_HOME` to the JDK directory.
The script locates `JAVA_HOME` from `java` and `ANDROID_HOME` from `~/Android/Sdk`
when possible. The SDK and Gradle downloads require network access in the build
qube. The generated Android project stays local and is ignored by Git.

In a Qubes TemplateVM, install system packages in the **template**, then restart
its AppVM; packages installed only in an ordinary AppVM do not persist. Keep the
Android SDK and Cargo tools in the development AppVM's home directory, or use a
dedicated development template. For a Fedora 43 template, run
`sudo dnf install java-21-openjdk-devel android-tools` in the **template**.
Do not install Android build tools in dom0.

The equivalent manual commands are:

```sh
# From the repository root:
cd apps/app
cargo install tauri-cli --version '=2.12.3' --locked
cargo install trunk --version '=0.21.14' --locked
sdkmanager "platform-tools" "platforms;android-37.0" "build-tools;37.0.0" "ndk;29.0.13846066"
export NDK_HOME="$ANDROID_HOME/ndk/29.0.13846066"
export CC_aarch64_linux_android="$NDK_HOME/toolchains/llvm/prebuilt/linux-x86_64/bin/aarch64-linux-android24-clang"
export CXX_aarch64_linux_android="$NDK_HOME/toolchains/llvm/prebuilt/linux-x86_64/bin/aarch64-linux-android24-clang++"
export AR_aarch64_linux_android="$NDK_HOME/toolchains/llvm/prebuilt/linux-x86_64/bin/llvm-ar"
rustup target add wasm32-unknown-unknown wasm32-wasip2 aarch64-linux-android
cargo build --locked --manifest-path ../../plugins/Cargo.toml --release --target wasm32-wasip2 -p core -p review
cargo tauri android init --ci --skip-targets-install
cargo tauri android build --ci --debug --target aarch64 --apk
```

For the Play Store, `RELEASE=1 scripts/build-android.sh` builds a release bundle
(`gen/android/app/build/outputs/bundle/universalRelease/app-universal-release.aab`) signed with
the upload key. `LOCORA_ANDROID_KEYSTORE` names its properties file (`storeFile`,
`storePassword`, `keyAlias`, `keyPassword`; default
`~/locora-deploy-setup/android/keystore.properties`), which never enters the repository;
`scripts/android-release-signing.py` adds the signing to the generated project. Raise `version`
in `src-tauri/tauri.conf.json` for every upload.

**Releases:** raise `version` in `src-tauri/tauri.conf.json` (and the workspace versions), merge
to `main`, then push a tag `vX.Y.Z` on that commit. `.github/workflows/release.yml` builds macOS
(Apple silicon and Intel), Windows, Linux (AppImage, deb, rpm), Android and the `locora` CLI and publishes them as
the GitHub release of that tag; a tag with a suffix (`v0.2.0-beta.1`) is a pre-release. For a
signed Android APK (the Play Store bundle is built locally and never published), set the repository secrets `ANDROID_KEYSTORE_BASE64`
(`base64 -w0 upload.jks`) and `ANDROID_KEYSTORE_PASSWORD`; without them the release carries a
debug-signed APK. The desktop installers are not code-signed.

CI uploads `locora-android-arm64-debug` from
`src-tauri/gen/android/app/build/outputs/apk/**/*.apk` (14-day retention).
This is a debug-key-signed, installable ARM64 APK, not a Play Store release/AAB.
No emulator, device test or release signing is performed.

#### Qubes: attach an Android phone for testing

Building the APK above does not require USB access. To install or debug it on a
phone, enable Developer options and USB debugging on the phone. In a **dom0**
terminal, list USB devices and attach the phone's `BACKEND:DEVID` to the
development qube (replace `locora-dev` and `sys-usb:2-5` with your actual
qube name and the ID shown by `qvm-usb`):

```sh
qvm-usb
qvm-usb attach locora-dev sys-usb:2-5
qvm-usb
```

Inside the **development qube**, run `adb devices` and confirm the phone's RSA
debugging prompt while it is unlocked. `adb` is part of Android platform-tools.
Then install the generated APK with `adb install -r <path-to-apk>`. After testing,
detach the device in **dom0**:

```sh
qvm-usb detach locora-dev sys-usb:2-5
```

If `qvm-usb` does not list the phone, inspect the cable/USB mode and whether a
USB qube exists. Do not create or reassign a USB controller without checking
Qubes' USB-keyboard guidance first: the only keyboard may share that controller.
If attaching an Android phone with USB debugging reports `usb-import: line 94:
echo: write error: Invalid argument`, check that `qvm-usb` lists the phone and
inspect `journalctl -k -n 80` in both `sys-usb` and the development qube after
the failed attempt. Qubes tracks this error for Android USB debugging in
[issue 9654](https://github.com/QubesOS/qubes-issues/issues/9654).

Android 11+ supports wireless debugging without an initial USB connection.
On the phone, enable **Developer options → Wireless debugging → Pair device
with pairing code**. In the development qube run `adb pair PHONE_IP:PAIR_PORT`
and enter the displayed code. Then use the phone's main Wireless debugging
screen for its potentially different connection port and run
`adb connect PHONE_IP:CONNECT_PORT`, followed by `adb devices`. The phone and
development qube must be able to reach each other over the network; pairing
and connection ports are usually different.
See the [Qubes USB guide](https://doc.qubes-os.org/en/latest/user/how-to-guides/how-to-use-usb-devices.html),
[USB-qube setup](https://doc.qubes-os.org/en/latest/user/advanced-topics/usb-qubes.html)
and [Android adb guide](https://developer.android.com/tools/adb).

### iOS: unsigned simulator app

Requires macOS, full Xcode selected via `xcode-select`, an iOS simulator runtime,
XcodeGen, CocoaPods and libimobiledevice. CI uses `macos-15` and selects the target
from the runner's architecture; no Apple team, certificate or provisioning secret
is needed. On a Mac, install the same CLI/Trunk versions as above, then:

```sh
cd apps/app # from the repository root
brew install xcodegen libimobiledevice
command -v pod >/dev/null || brew install cocoapods
xcodebuild -version
xcrun --sdk iphonesimulator --show-sdk-version
# If no iOS simulator runtime is installed:
# xcodebuild -downloadPlatform iOS
case "$(uname -m)" in
  arm64) target=aarch64-sim; rust_target=aarch64-apple-ios-sim ;;
  x86_64) target=x86_64; rust_target=x86_64-apple-ios ;;
esac
rustup target add wasm32-unknown-unknown wasm32-wasip2 "$rust_target"
cargo build --locked --manifest-path ../../plugins/Cargo.toml --release --target wasm32-wasip2 -p core -p review
cargo tauri ios init --ci --skip-targets-install
cargo tauri ios build --ci --debug --target "$target" --no-sign
```

The CLI target names differ from Rust target triples. Output is
`src-tauri/gen/apple/build/arm64-sim/Locora.app` on Apple Silicon, or
`src-tauri/gen/apple/build/x86_64/Locora.app` on Intel. CI packages the bundle with
`ditto` and uploads `locora-ios-simulator` (14-day retention). This is not an IPA
and cannot be installed on an iPhone. Device/App Store builds need a separate
signing/provisioning setup and device validation.

### Verification limits

These workflows are build checks, not proof that Phase 2's device behavior, E2E
click budgets, accessibility or startup-time requirements pass. Remote CI has not
been run as part of adding them. Local validation cannot replace Android SDK/NDK
and macOS/Xcode builds. Dependency, SDK and generated Gradle downloads require
network access.

The dialog plugin has no folder picker on mobile, so TOML export (`dump_pick`)
returns an explicit error there; `.locora` export works. Picked Android `content://`
files and iOS security-scoped files are streamed through the native filesystem
plugin into bounded private temporary files. The mobile import dialog accepts
`.locora` archives; TOML with relative media needs a shared directory that
document providers do not grant. The plugin host selects Wasmtime/Pulley on iOS to avoid
JIT executable-memory restrictions; actual device operation still needs a signed
build and hardware test.
No release or device-readiness claim is implied by an uploaded build artifact.

## How it fits together

- `src-tauri/src/views.rs`: start screen and room view from store + review schedule
- `src-tauri/src/journey.rs`: a journey over IPC, same plan and grading as `locora practice`
  (`locora_runtime::journey`, Core plugin)
- `src-tauri/src/sply.rs`: `.sply` → interactive SVG with the vendored Splinely runtime,
  served as `locora://localhost/sply/<sha256>`. The graphic is mounted inline in the page
  (`splinely-mount.js`), not in a frame; its messages go through `sply_bridge.js`
- `ui/src`: screens (start, palace with rooms and markers, journey); no domain logic

## Locus pictures

Revealing a locus shows its picture at the locus position as well as in the answer
panel. Its width is `image_size` of the room width (default 0.25, range 0.05–1).
Raster pictures retain their aspect ratio; `.sply` frames have a square viewport.
Before reveal only the marker is shown. Reverse practice keeps the picture in the
question rather than placing it on the stage as an answer.

Enable **Bearbeiten** in a palace room to edit places, items, notes, Recall/Guess/
Quiz answers and picture widths inline. Valid
content saves automatically; incomplete or invalid input stays visible until
corrected or discarded. Navigation is blocked while edits are pending. Click the
stage in **Ort setzen** mode to add a locus, drag markers to move them, or focus a
marker and use arrow keys (Shift for larger steps). A button also adds a locus at
the center. Reveal a picture to use its resize handle; its numeric width field is
the keyboard alternative. Deletion requires a second confirmation.

In **Bearbeiten**, focus the stage and paste with Ctrl/Cmd+V, or paste into
**Liste einfügen** and choose **Liste als Route hinzufügen**. Each nonempty trimmed line becomes a Recall item at a new numbered
place. Limits: 100 items, 500 UTF-8 bytes per item, 64 KiB input. New places are
appended in list order along an inset serpentine route; existing places are not
moved. Drag or use arrow keys to adjust positions. Video rooms reject lists.
The backend checks exact palace/room ownership and all items; the store commits
the entire batch and operation log in one transaction or rolls everything back.
Failed textarea submissions retain the text; successful submissions clear it.
Stage paste uses the clipboard event, without requesting clipboard permissions.
Ordinary paste in other input fields is never intercepted.
The list is an explicit submission, not an autosaved or durable draft.

**Bild wählen…** opens a native file picker for the selected locus; **Bild entfernen**
autosaves removal. Supported: PNG, JPEG, WebP, GIF, AVIF and binary `.sply`, up to
500 MiB. The backend reuses source/CLI extension classification, checks raster MIME
signatures and validates `.sply` with the existing SVG converter. Cancellation is a
no-op; errors appear in German and leave the current assignment intact. Choose only
when edits have saved; form input is disabled while the picker is open. Files are
copied into the profile media store, so originals need not remain in place.
Only exact palace/room/locus IDs cross IPC, never a file path. The dialog plugin is
backend-only: no dialog/filesystem permissions were added to the WebView and CSP
is unchanged. Mobile content-URI selections are not supported yet (local files only).
Native dialog interaction still needs a manual desktop/WebView smoke test.

## New palace from media

On Home, **Bild/Video wählen…** opens the backend-only native picker for the same
pictures plus MP4/M4V, WebM and MOV. Extension and content signatures must match;
regular local files only, bounded to 500 MiB (also for video). This checks signatures,
not complete video decoding. The filename stem names the palace and first room
(fallback **Neuer Palast**); existing palace names get ** (2)**, ** (3)**, etc.,
using the store's NOCASE comparison. The room type follows the media type.
Success opens the returned snapshot directly in editing mode; Back reloads Home.
Cancellation writes nothing. Media metadata, palace, room and operation log commit
in one transaction; failures leave no empty palace or partial database writes.
Immutable unreferenced hash files can remain after a database failure.
No paths cross IPC and no WebView permissions or CSP changes are needed.
Tests cover cancellation, invalid signatures, size limits, persistence, name
collisions and SQL rollback. Native desktop/WebView interaction remains unverified.

Drag-and-drop uses a single-use ticket: the native window event keeps the path in
the backend (30 s, one file) and the WebView only receives the ticket. Drop on Home
creates a new image/video palace; drop in the editor sets the selected locus's
picture. Browser (HTML) drops are rejected.

Undo/redo (buttons, Ctrl/⌘+Z, Ctrl/⌘+Shift+Z or Y outside text fields): content,
picture, move and resize use inverse patches; add, paste and delete use opaque,
single-use backend receipts (`editor_receipts`, newest 500 kept) that refuse to
overwrite changed loci or occupied route positions. Review state is never deleted.
History is per room and in memory. Every raw form revision is also kept in
`localStorage`; after a crash the editor reopens the locus and offers restore or
discard. Content with workbook bindings stays read-only; geometry remains editable.
CLI `add/edit --image-size` and `image_size` in `locora.toml`
remain available. Browser reload protection is best-effort; do not close the app
while an error or pending edit is shown.

Rust tests cover editor mutations, validation, persistence, geometry helpers and
incomplete draft parsing, list parsing/route geometry, batch persistence and rollback
(including database failures). Browser/WebView list submission, gesture and autosave-focus checks remain
pending; see [`docs/app-editor-testplan.md`](../../docs/app-editor-testplan.md).
